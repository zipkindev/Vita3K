# Bounded state history and recoverable pipeline preparation (.43)

Based on .42, with async pipeline compilation unchanged. The frozen .41 Sebenco input (214 exact recipes) remains the comparison seed; .42's two newly learned recipes are not injected into this candidate's baseline.

History holds at most 64 complete observed recipes, at most eight per shader pair and interlock class. Different shaders sharing identical fixed state retain separate associations. Re-observation refreshes recency without advancing the knowledge generation; genuinely new recipes advance it. Ready draws refresh history once per 64 retrievals, before ready-object/ready-cache returns. Exact fixed state, texture hints and render-pass compatibility remain required. No unrelated shader cross-product is compiled.

Prediction uses exact recipe ownership rather than suppressing every later state after a pair's first draw. Existing exact-job owners and actually observed recipes are checked before shader probes/conversion and checked again before publication. Learned exact recipes remain ahead of actual bindings, then creation hints. Admission remains 16 live predictions / four hint objects, actual burst eight plus four admissions per second, hint burst two plus one per two seconds; worker ceilings stay one active-render / two quiet-time.

Up to 64 parked requests retain their bindings for recovery; up to 64 queued/running requests are separate owners. A parked request can reopen when history or shader/program readiness changes. Temporary render-busy/admission pressure retries with 250 ms–2 s bounded backoff, not a lifetime attempt cap. New knowledge can reopen immediately. Each worker scan visits at most 64 parked requests and requeues at most four; a rotating key cursor avoids always serving the same identities. Oldest parked requests are evicted deterministically when full. A single request transfers ownership between queued, running and parked states under warm_mutex; workers never mutate a request after publishing it to another owner. Shutdown joins workers and disposes both queues. No driver object destruction is added to the guest thread.

Coverage retains first queued QPC, last attempt timing, attempt count, aggregate outcome bits and hint/actual-source bits. Existing outcome bits remain: observed/drawn=1, unavailable vertex shader=2, unavailable fragment shader=4, empty history=8, compile failure=16, prepared=32, exception=64, unavailable admission=128, exact object owned=256, render/global-object pressure=512. New bits: unrelated state=1024, invalid recipe=2048, stopped=4096. Reasons may coexist across candidate states. New nested profiling kinds shader_retrieve (28) and driver_create (29) split CPU-side shader work from monolithic driver pipeline creation; they overlap outer compile spans and must not be added to them.

This is a deterministic policy driven by observed game state, not a game/track-specific recipe table or automatic frame-time controller. Bounds and rates are explicit, not dynamically inferred from frame latency. A truly new effect whose usable state becomes known only milliseconds before its draw may still compile synchronously. No <50 ms guarantee is made.

## Recorded-command lookahead investigation

The existing SceGxmContext::prepare_pair already announces actual shader bindings on the guest side, before render execution. A complete recipe is described later from VKContext: render-pass compatibility, actual color/depth state, surface casts and draw-specific texture hints are only established there. Scanning queued commands without a separate state interpreter and immutable resource ownership would use incomplete or mutable state and risk changing draws. Therefore .43 does not add speculative command execution, render reordering, guest pointers in workers, pipeline libraries or async draw-skipping. Full-state lookahead remains a separate implementation requiring differential state-replay and resource-lifetime tests. The new source/origin and retry coverage provides evidence to decide whether it would offer useful lead time.

## Validation

Standalone C++20 tests cover same-state/different-shader associations, history refresh, interlock isolation, per-pair/global eviction over changing identities, transient backoff, clock regression, immediate material-change recovery and 10,000 later retry opportunities. Existing admission and queue tests remain required. Native Windows optimized compilation and full CTest suite, matching EXE/PDB identity, package provenance and separate staging must pass before release or performance claims.
