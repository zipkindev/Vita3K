# JIT preparation prototype .20

This test candidate adds opt-in **CPU → JIT Preparation → Learn and Prepare Main-Thread Code (Experimental)** to the exact `.19` diagnostic source. It targets first-use main-thread compilation identified in a WipEout 2048 Chenghou Rapier trace. No gameplay improvement is claimed before comparison. Texture policy and 512 MiB budget, Vulkan async eligibility, pipeline workers and guest scheduling remain unchanged.

Play a learning session with the option enabled, then close normally. On a later fresh launch, eligible learned blocks can be compiled before the main guest thread starts. This prototype prepares at application startup; it does not recognize individual race loading screens. The first session has no reusable preparation profile, and the existing diagnostic CSV cannot be imported as one.

Preparation is compile-only: it does not execute ARM instructions or restore native machine code. It uses the owning, nonexecuting JIT and the full PC/Thumb/endian/FPSCR/IT descriptor. Profiles are tied to title, version, executable, CPU optimization mode, pinned backend/hook schema, loaded addresses and SHA256 of the main module's read/execute segments. Writable segments, external modules, misaligned/reserved/stepping descriptors, incomplete/invalid/oversized read traces and compilation across invalidation are excluded. Every instruction and translation-hook read must match the stored ordered address/value/type sequence; reads are checked again immediately before native emission. A mismatch, pending invalidation or insufficient code-cache headroom falls back to normal demand compilation. Normal invalidation remains active afterward. Concurrent mutation of a live JIT is not used.

Bounds: 2,048 blocks, 256 reads per block, four-way bounded cost-priority learning; observations under 50 microseconds are excluded. Startup attempts are limited to 1.5 seconds and 8 MiB of emitted native code, checked between blocks; the final block may exceed either limit. Preparation does not deliberately flush a full code cache to make room. Exceptions discard the speculative JIT before demand fallback. Main-thread-only learning adds bounded work during compilation misses; ready JIT hits are unchanged. No other guest CPU is warmed in this prototype.

Profiles are local game-derived instruction manifests, not distributable emulator binaries. They are stored in portable cache `jit-preparation/<TITLE>.pj20`, with a JSON preparation/learning report. A checksum rejects accidental corruption; current code and identity validation authorize reuse, not the checksum alone. At most 16 MiB per game and 64 MiB of completed profiles total; oldest-written profiles are evicted when saving. A pending replacement/backup can temporarily add storage above that limit. Save occurs only after normal CPU shutdown. To reset learning, close the emulator and delete that game's `.pj20` cache file. Disabling the option preserves the profile and uses normal compilation. Saves, shader caches and learned texture profiles are separate.

Validation includes ARM/Thumb prepared versus demand execution, no register/extended-register/flags/memory/SVC effects during preparation, changed-code rejection, pending and normal invalidation, cached blocks, profile identity/corruption/record bounds and restart/configuration/UI wiring. Full Windows results and exact EXE/PDB provenance must be checked before staging. Release remains a diagnostic candidate; `.19` is preserved as reference. Vita3K, Vita3K-Plus and Vita3K-nx contributions and licenses remain acknowledged in the repository README.
