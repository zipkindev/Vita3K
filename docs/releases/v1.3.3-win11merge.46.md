# Vita3K-Go .46 — Progress-driven pipeline recovery candidate

**Windows x64 prerelease / release candidate.** Optimized candidate
focused on Lenovo Legion Go. Built on Vita3K, Vita3K-Plus and selected Vita3K-nx
changes; original authorship and licenses remain preserved. Broader title/device
coverage and consistently sub-100 ms gameplay are not established.

## Changes since .38

- Vulkan correctness fixes cover readback/attachment ordering, copied-texel
  writeback barriers, fallback attachment usage, storage-view cleanup and sRGB
  view usage. Graphics pipeline libraries remain disabled by default.
- Bounded preparation follows observed pipeline state and exact learned recipes.
  Active request ownership survives prediction reclamation; stale predictions can
  be recycled without losing recoverable work.
- Drawn-key history survives full-template eviction. Recovery probes and retries
  are bounded; useful new readiness can reopen work without waiting through an
  unrelated old cooldown. Unchanged pressure retains backoff.
- Redundant pair notifications and unchanged worker wakeups are suppressed.
  Up to 2,048 completed speculative recipe identities prevent repeatedly creating
  the same unused prediction after its live object is reclaimed.
- Renderer-path OS prefetch was removed; fresh useful pipeline work takes priority.
  Useful prepared predictions can contribute to subsequent learned recipes.

The changes retain automatic per-game texture learning, bounded profile merging,
parallel PVRTC decoding and the configurable decoded-texture cache. No additional
workers, prediction slots, compile-rate allowance or decoded RAM budget are added
by .46. See [recovery behavior and limits](../PIPELINE-PROGRESS46.md).

A completed prediction record is not a retained Vulkan pipeline object. Required
first use can still recreate a reclaimed object. New effects without a complete
known recipe can still incur synchronous driver compilation. Full native recipe
preparation independent of guest bindings is not implemented by this candidate.

## Validation and performance scope

All **38 native Windows tests passed**. Package CRC/payload hashes and matching
native EXE/PDB symbol lookup passed. A separate pinned Khronos synchronization-
validation menu smoke recorded zero error categories and 13 unused shader-output
warnings. This establishes menu coverage, not error-free race/effect rendering.

Performance testing uses validation **OFF**, async compilation **OFF**, Vulkan
**2×**, anisotropic filtering **4×**, Bilinear, VSync/shader cache on, external-host
mapping, surface synchronization and high accuracy enabled, automatic texture
preparation/two-way decoding and a **512 MiB** decoded cache. Diagnostic observers
are enabled for investigation and add work; routine play can leave them off.

The .45 four-track Rapier tournament was reported smooth overall with very few
microstutters. Its recorder includes loading/results and different learned input
from .46; it is not a controlled version-to-version speedup comparison.

An initial .46 two-minute capture was accidentally a solo seven-lap time trial,
with no traffic/weapons and unverified phase boundaries: median **33.34 ms**, p99
**35.91 ms**, maximum **227.94 ms**, two intervals ≥50 ms and one ≥100 ms.
The largest interval overlapped a **213.69 ms synchronous pipeline compile** for a
recipe absent from the input profile. That result cannot establish combat gains.
The subsequent intended Sol 2 Rapier combat window recorded median **33.34 ms**,
p99 **36.19 ms**, maximum **525.08 ms**, five intervals ≥50 ms and two ≥100 ms.
The largest gap overlapped a **510.07 ms driver pipeline creation** inside a
synchronous compile. Continuous driving with traffic/weapons and some stutters was confirmed. Exact
click-to-driving alignment is not instrumented.
The closed session saved 241 exact recipes, up from 236. This does not establish
a .45/.46 speedup or sufficient first-use coverage.

Measurements are frame-presentation intervals, not controller-to-display latency.
Earlier cache and DOA5 observations, their settings and comparison limits remain
in [performance findings](../performance-findings.md). No general percentage
speedup, guaranteed hitch elimination or other-device validation is claimed.
